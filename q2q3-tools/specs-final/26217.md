The change is checked by unit tests that use the following code locations and signatures. Create or extend them exactly as named. Everything else about the implementation is up to you.

**New file `packages/features/auth/signup/constants.ts`**, exporting:

**New file `packages/features/auth/signup/lib/fetchSignup.ts`**, exporting:
```ts
type SignupData = {
  username?: string;
  email: string;
  password: string;
  language: string;
  token?: string;
};
type SignupSuccessResponse = {
  message: string;
  stripeCustomerId?: string;
};
type SignupErrorResponse = {
  message: string;
  checkoutSessionId?: string;
};
export type SignupResult =
  | { ok: true; data: SignupSuccessResponse }
  | { ok: false; status: number; error: SignupErrorResponse };
export async function fetchSignup(data: SignupData, cfToken?: string): Promise<SignupResult>
export function isUserAlreadyExistsError(result: SignupResult): boolean
export function hasCheckoutSession(result: SignupResult): result is { ok: false; status: number; error: SignupErrorResponse & { checkoutSessionId: string } }
```

**Prisma calls the tests stub** (through `prismaMock`): `user.findUnique`, `user.findFirst`, `team.findUnique`, `verificationToken.delete`; `user.upsert` for a signup with an invite token, and `user.create` for a signup without one (in both handlers). Unique-constraint errors are instances of the mocked `Prisma.PrismaClientKnownRequestError` from `@calcom/prisma/client` (the mocked `Prisma` defines only that class, with `code` and `meta.target`).

**How the tests call the handlers:** the mocked `NextResponse.json` throws unless it is given an explicit `{ status }`. `calcomHandler`'s default export stays `usernameHandler(handler)`; the tests' `usernameHandler` mock captures the inner `handler`.
