Add PKCE support to the Cal.com OAuth provider so public clients without a client secret can use it. OAuth clients become either confidential or public. In the OAuthClient and AccessCode models (`packages/prisma/schema.prisma`, with a migration), the client gets a type that defaults to confidential and its secret becomes optional, and access codes store the code challenge and method. Add a new PKCE helper in `packages/lib/pkce.ts` that accepts only S256 as a challenge method and verifies a code verifier against a stored challenge.

In the tRPC OAuth client router (`addClient.handler.ts`, `generateAuthCode.schema.ts`), adding a client takes a PKCE option: with it the client is stored as public with no secret, without it as confidential with a generated secret as today. The admin OAuth settings form at /settings/admin/oAuth gets a "Use PKCE" switch for this. Generating an auth code accepts an optional code challenge and method (S256 required when given) and stores them on the access code. The OAuth authorize page passes code_challenge and code_challenge_method through.

In the OAuth provider endpoints, the token and refresh routes read the client type and the stored challenge: confidential clients must send a valid client_secret, public clients must send a code_verifier that matches the stored challenge via the PKCE helper, and a confidential client that used PKCE must also send the code_verifier on token exchange and refresh. Refresh accepts the refresh token in the body or the Authorization header, and both routes return token_type and expires_in with no-store cache headers. Existing confidential clients keep working unchanged.
